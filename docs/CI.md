# CI and Dependabot

Three workflows in `.github/workflows/`. `ci.yml` lints and tests, and pulls
co-core's wheelhouse by WIF as the read-only `co-pypi-reader` SA. `audit.yml`
reads `uv.lock` against OSV, report-only (#86). `context-cadence.yml` is
generated by the vendored `install-cadence.sh` ([SKILLS.md](SKILLS.md)).

## Pins (#88, #90)

Every `uses:` in `ci.yml` and `audit.yml` is `owner/action@<40-hex sha> # vX.Y.Z`.
setup-uv publishes no floating major since v8, and a tag can be moved. When a
pin moves, check the SHA against its tag:

```bash
gh api repos/<owner>/<action>/git/ref/tags/<tag> --jq '.object.type + " " + .object.sha'
```

`commit`: that SHA is the pin. `tag`: an annotated tag, whose SHA names the tag
object, not a commit; the pin is the commit it points at,
`gh api repos/<owner>/<action>/git/tags/<sha> --jq .object.sha`. Pinned by
`tests/deploy/test_workflow_pins.py` and `tests/deploy/test_dependabot.py`.

## Dependabot (#90)

`.github/dependabot.yml` proposes action bumps only: `github-actions`, weekly,
one PR per action, `chore:` subjects. No `uv`: co-core resolves from the private
wheelhouse, which Dependabot's updater cannot sync (#86).

**`context-cadence.yml` is excluded** (`exclude-paths`). A re-render reverts any
bump made in it (gregoryfoster/skills#373), so its `actions/checkout@v5` moves
with the installer: re-run `install-cadence.sh` after the skills submodule
brings a new template. `exclude-paths` lists no ecosystem limit in GitHub's
[Dependabot options reference](https://docs.github.com/en/code-security/reference/supply-chain-security/dependabot-options-reference#exclude-paths),
and dependabot-core applies it in the base fetcher's `repo_contents`
(`common/lib/dependabot/file_fetchers/base.rb`, `filter_excluded`, read at
`00f6c78`), which the `github-actions` fetcher lists `.github/workflows/` through.

**A Dependabot run reads its own credential context.** GitHub runs it as if
from a fork: a read-only `GITHUB_TOKEN`, Dependabot secrets only. `ci.yml` needs
no secret: it needs `vars.GCP_WIF_PROVIDER` to resolve and the OIDC token that
`id-token: write` asks for. Both held on CannObserv/watcher's Dependabot PRs
(same provider, same SA): `pull_request` runs as `dependabot[bot]`, WIF auth and
wheelhouse sync green (watcher#356, 2026-10-09; #364, 2026-10-11). broker's first
PR is the confirmation here. On a red one, read **Authenticate to Google Cloud**
first. Watcher's `docs/COMMANDS.md` maps its errors: *"must specify exactly one
of workload_identity_provider or credentials_json"* means the variable did not
reach the run; *"did not inject $ACTIONS_ID_TOKEN_REQUEST_TOKEN"* means no OIDC
token; past both, the provider's attribute condition or the SA binding. None is
the bump's fault, so a red there is fixed on the CI side, not by taking the bump.

**How one lands: fast-forwarded on the node, like every other change.**

```bash
# Read the action's release notes, not just the diff: a major can change inputs.
gh pr comment <N> --body "@dependabot rebase"   # only if main moved; wait for the force-push
gh pr checks <N> --watch                        # green on the commit that lands
# the PR's new SHA is its tag's commit: check it as Pins, above
git fetch origin "$(gh pr view <N> --json headRefName -q .headRefName)"
git merge --ff-only FETCH_HEAD
git push origin main                            # GitHub marks the PR merged
```

Fast-forward only: the commit CI tested is the one that lands, and its subject
already takes AGENTS.md's form (`chore: bump ...`). One PR at a time; after each
push the next may need `@dependabot rebase`. `~/broker` is the bus-health and
backup units' `WorkingDirectory`: merge on `main`, never switch branches there.
Nothing restarts: an action bump touches `.github/` alone.
