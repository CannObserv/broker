# CI and Dependabot

Three workflows in `.github/workflows/`. `ci.yml` lints and tests, and pulls
co-core from the co-pypi index by WIF as the read-only `co-pypi-reader` SA
([below](#the-co-pypi-index-144)). `audit.yml`
reads `uv.lock` against OSV, report-only (#86). `context-cadence.yml` is
generated by the vendored `install-cadence.sh` ([SKILLS.md](SKILLS.md)).

## Shell lint (#112)

`scripts/shellcheck.sh` lints this repo's own shell scripts: every tracked
`*.sh` and `.githooks/*`, never a symlink (the `.claude/hooks/` ones point into
`skills-vendor/`) and never `.skills/` (the vendored refresh hook rewrites
`doctor.sh`). A finding in either is an issue on gregoryfoster/skills. `ci.yml`
runs it over the tree as a step of `lint + test`; a new job would need a
`CI_JOBS` entry in `scripts/deploy.sh`. A commit runs it over what is staged,
with ruff, once the clone opts in:

```bash
git config core.hooksPath .githooks
```

The hook is per clone and `--no-verify` skips it, so CI is the enforcement.
Both run shellcheck 0.11.0 from `shellcheck-py` in `uv.lock`'s `lint` group, a
hash-pinned wheel: no root install, no fetch at run time, `audit_lock.sh` reads
it. A bump changes what the gate finds, so it lands with its fixes:
`uv lock --upgrade-package shellcheck-py`, then `bash scripts/shellcheck.sh`.
Fix a finding rather than disable it; a `# shellcheck disable=` that stays
gives its reason on the same line. Pinned by `tests/deploy/test_shellcheck_gate.py`.

## Pins (#88, #90)

Every `uses:` in `ci.yml` and `audit.yml` is `owner/action@<40-hex sha> # vX.Y.Z`.
setup-uv publishes no floating major since v8, and a tag can be moved. When a
pin moves, check the SHA against its tag:

```bash
gh api repos/<owner>/<action>/git/ref/tags/<tag> --jq '.object.type + " " + .object.sha'
```

`commit`: that SHA is the pin. `tag`: an annotated tag, whose SHA names the tag
object, not a commit; the pin is the commit it points at,
`gh api repos/<owner>/<action>/git/tags/<sha> --jq .object.sha`. Pinned by
`tests/deploy/test_workflow_pins.py` and `tests/deploy/test_dependabot.py`.

## Dependabot (#90)

`.github/dependabot.yml` proposes action bumps only: `github-actions`, weekly,
one PR per action, `chore:` subjects. No `uv` version updates: co-core's pin
moves as a registration (#104, #114). Security updates need no entry and no
`registries:` key ([below](#the-co-pypi-index-144)).

**`context-cadence.yml` is excluded** (`exclude-paths`). A re-render reverts any
bump made in it (gregoryfoster/skills#373), so its `actions/checkout@v5` moves
with the installer: re-run `install-cadence.sh` after the skills submodule
brings a new template. `exclude-paths` lists no ecosystem limit in GitHub's
[Dependabot options reference](https://docs.github.com/en/code-security/reference/supply-chain-security/dependabot-options-reference#exclude-paths),
and dependabot-core applies it in the base fetcher's `repo_contents`
(`common/lib/dependabot/file_fetchers/base.rb`, `filter_excluded`, read at
`00f6c78`), which the `github-actions` fetcher lists `.github/workflows/` through.

**A Dependabot run reads its own credential context.** GitHub runs it as if
from a fork: a read-only `GITHUB_TOKEN`, Dependabot secrets only. `ci.yml` needs
no secret: it needs `vars.GCP_WIF_PROVIDER` to resolve and the OIDC token that
`id-token: write` asks for. Both held on CannObserv/watcher's Dependabot PRs
(same provider, same SA): `pull_request` runs as `dependabot[bot]`, WIF auth and
the wheelhouse sync of the time green (watcher#356, 2026-10-09; watcher#364, 2026-10-11). broker's first
PR is the confirmation here. On a red one, read **Authenticate to Google Cloud**
first. Watcher's `docs/COMMANDS.md` maps its errors: *"must specify exactly one
of workload_identity_provider or credentials_json"* means the variable did not
reach the run; *"did not inject $ACTIONS_ID_TOKEN_REQUEST_TOKEN"* means no OIDC
token; past both, the provider's attribute condition or the SA binding. None is
the bump's fault, so a red there is fixed on the CI side, not by taking the bump.

**How one lands: fast-forwarded on the node, like every other change.**

```bash
# Read the action's release notes, not just the diff: a major can change inputs.
gh pr comment <N> --body "@dependabot rebase"   # only if main moved; wait for the force-push
gh pr checks <N> --watch                        # green on the commit that lands
# the PR's new SHA is its tag's commit: check it as Pins, above
git fetch origin "$(gh pr view <N> --json headRefName -q .headRefName)"
git merge --ff-only FETCH_HEAD
git push origin main                            # GitHub marks the PR merged
```

Fast-forward only: the commit CI tested is the one that lands, and its subject
already takes AGENTS.md's form (`chore: bump ...`). One PR at a time; after each
push the next may need `@dependabot rebase`. No unit runs `~/broker` since
#108 (both run `/srv/broker/live`), but `scripts/deploy.sh` runs from it: merge
on `main`, never switch branches there. Nothing restarts and nothing deploys:
an action bump touches `.github/` alone.

## The co-pypi index (#144)

co-core resolves from cannobserv's Artifact Registry index,
`https://us-west1-python.pkg.dev/co-gcs/co-pypi/simple/`, and only co-core does:
the index is `explicit` and `[tool.uv.sources]` pins the one name to it
(`pyproject.toml`; `tests/deploy/test_dependency_index.py`). The name is
unclaimed on PyPI (cannobserv#615), so nothing may ever look for it there.
#144 retired the GCS wheelhouse, `scripts/sync_wheelhouse.py` and #125's digest
table: `uv.lock` holds each file's sha256 as the index served it.

**Who holds a token.** One identity reads the index everywhere: the
`co-pypi-reader` SA, `artifactregistry.reader` on `co-pypi`.
- CI: `ci.yml`'s WIF step also mints an access token (`token_format:
  access_token`), and the `uv sync` step alone takes it, as
  `UV_INDEX_CO_PYPI_USERNAME` / `_PASSWORD` from the action's masked output.
  `uv lock --locked` reads the lock alone (measured offline), so it needs none.
  `tests/deploy/test_workflow_pins.py` holds the token to that one step.
- The node: `/etc/broker/co-pypi-reader.json`, `root:exedev` `0640`
  (`BROKER_CO_PYPI_KEY` overrides the path; `GOOGLE_APPLICATION_CREDENTIALS`
  never does). `scripts/co-pypi.sh <uv command>` mints a one-hour token with
  `scripts/co_pypi_token.py` and execs the command with the pair set. It starts
  from an allowlisted environment, so a sourced `.env`'s PATs reach neither uv.
  `scripts/deploy.sh` runs each build's sync through it (deploy/README.md,
  *Environment*); a dev tree runs its own syncs and every `uv lock` the same way
  (AGENTS.md). Its one dependency, `google-auth`, is the lock's `co-pypi` group,
  from PyPI, run `--frozen`.

A mint that fails names the key path and the exception, never the token. A
`401` from the index with a token set is the SA's binding on the repository;
without one, a uv command that should have gone through the wrapper.

**The cache.** `ci.yml`'s setup-uv sets `prune-cache: true`: the repo is
public, and an unpruned cache would hold co-core from the private index. The
prune drops downloaded wheels and keeps built ones, so it covers co-core only
while the lock has a wheel for each co-core; `tests/deploy/test_dependency_index.py`
checks that.

**Dependabot security updates** move `uv.lock` without a `dependabot.yml`
entry. The updater reads the index over OIDC through the org registry
`PYTHON_INDEX_OIDC_GCP`, keyed on the index URL byte for byte, once an org owner
admits this repository (ID `1353004854`) to it and to the `github-dependabot`
WIF provider's condition (cannobserv `docs/DEPENDABOT.md`, step 3). Until then
a security update fails before it opens anything; this repo's token gets 403 on
the registry API, so admission is read in the org's UI. A security PR lands by
hand, as processor's do: check every co-core `source` in the proposed `uv.lock`
is still the index URL, since the updater asks PyPI first.
